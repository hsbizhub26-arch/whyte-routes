## Resolved

### [P1] Map locate/zoom controls hidden behind bottom drawers — RESOLVED
- **Symptom:** The circular locate / re-center button (and the zoom column) on the
  map was vertically centered on the right edge, so a bottom sheet rising over the
  map swallowed it. On the owner Home / Fleet Dashboard the "Dashboard" panel hid
  the locate button entirely and clipped the zoom control; the driver My Route
  status card posed the same risk.
- **Fix:** Re-anchored the control column to `.bottomTrailing` with a **dynamic**
  bottom clearance that always sits above the tab bar + home indicator and lifts
  above whatever bottom card/panel is showing (measured, not hardcoded).
  - Owner fleet map ([`LiveFleetMapView`](WHYTE ROUTES/Views/Owner/LiveFleetMapView.swift) +
    [`OwnerDashboardView`](WHYTE ROUTES/Views/Owner/OwnerDashboardView.swift)) — commit `de2e7e0`.
  - Driver map ([`DriverMapView`](WHYTE ROUTES/Views/Driver/DriverMapView.swift) +
    [`DriverDashboardView`](WHYTE ROUTES/Views/Driver/DriverDashboardView.swift)) — hardened
    proactively in the same pass; controls now clear the measured status card.
- **Verified:** simulator build clean (zero errors/warnings in the touched files);
  confirmed on-device in both collapsed and open/expanded states, both views.

### [P1] No way to arrive from live navigation; runaway at-property timer — RESOLVED
- **Symptom:** The navigation screen offered only *End* and *Mark Completed*. Arriving
  meant backing out to the stop screen, and the at-property timer never showed during
  navigation (`atPropertyElapsed` was always passed `nil`). Separately, a *scheduled*
  stop carrying a leftover `arrivedAt` showed "At property: 163:49:38".
- **Fix** — commit `04a03f3`:
  - "I've Arrived" fallback on the navigation screen, shown only within 200m of the
    stop's pin by straight-line distance (latched until 300m), outlined so it can't be
    mistaken for Mark Completed.
  - `markArrived` idempotent across its three entry points (geofence, stop screen, nav
    screen) and refused while a completion is saving.
  - Timer gated on `status == .arrived`; no age ceiling (storm visits run 20h+).
  - Navigation recentre chip now clears the *measured* card instead of a fixed 210pt.
- **Note:** Arriving ends navigation by design (releases voice + audio session), so the
  timer runs on the stop screen after arrival, not on the navigation screen.
- **Verified:** Xcode 27.0 build clean (zero errors/warnings); two adversarial review
  rounds. **Not yet exercised on a device** — test on TestFlight Build 51.

## Open — tech debt

### [P1] Owner "reset" never clears a stop's timestamps (root cause of the 163h timer)
- `EditRouteView.toggleCompletion`'s un-complete branch sets `enRouteAt` / `arrivedAt` /
  `completedAt` to `nil`, but writes through `StopsRepository.updateStop`, which uses
  `setData(toDict(), merge: true)` — and `toDict()` omits nil fields. So the reset never
  deletes them: Firestore keeps the old timestamps. The *first* tap of a
  complete-then-reset also stamps a `completedAt` that is never removed.
- **Impact:** the 163-hour timer, and `DriverTimeReportView` filing re-opened stops under
  the wrong shift. This directly undermines the planned liability defense log, whose
  whole value is trustworthy timestamps.
- **Fix:** in the reset path write `FieldValue.delete()` for the three fields (the `put()`
  pattern `saveRouteEdits` already uses). Don't change `updateStop` globally.
- **Live data:** the demo reviewer account's Yard and Webber yard stops still carry stale
  `arrivedAt` / `enRouteAt` / `completedAt`, and Build 50 shows its timer whenever
  `arrivedAt` is set. Delete those fields by hand in the Firebase console.

### [P1] Sign-in form clears itself for ~8s before the dashboard loads
- `OwnerLoginView.login()` drops `isLoading` the instant Firebase returns, then the view
  re-renders with an empty password while the workspace resolves. Drivers read it as a
  failed login. Keep the loading state until the role/company has resolved.

### [P1] Start Shift sits on "Starting..." for ~17s
- Not yet diagnosed. The shift write itself is one read + write, and End Shift completes
  in under half a second, so something else in the start path is stalling.

### [P2] Navigation session can reuse the previous stop's route
- `NavigationSession.stop()` doesn't cancel an in-flight `calculateRoute` (reroute Task or
  the location sink's Task); the late response still writes `route` / `remainingDistance`.
  `start(to:)` doesn't reset `route`, so the next stop's navigation can begin tracking
  the *previous* stop's route until a reroute. `remainingDistance` also freezes once the
  last step completes. After the `await` in `calculateRoute`, bail unless still navigating
  to the same destination, and reset state in `start(to:)`. Turn-by-turn engine — change
  carefully and road-test. (The arrive fallback no longer depends on these values.)

### [P2] Stops left "arrived" at end of shift are never closed or flagged
- `endShift` doesn't close out stops still `arrived`. Next storm, completing one records
  days of service time. Close or flag them at end of shift — matters for the liability log.

### [P3] Navigation recentre chip in landscape
- The chip clearance has a floor but no ceiling, so in landscape on small phones the chip
  can sit under the maneuver banner. Not a regression (the old fixed 210pt had the same
  problem in landscape). Clamp against the banner's bottom edge, or lock nav to portrait.

### [P3] Thumb carry-over onto Mark Completed after an automatic arrival
- If the geofence fires as a driver reaches for the nav-screen fallback, the cover
  dismisses and the tap can land on the stop screen's Mark Completed, which is
  irreversible (sends the completed text). Consider a ~1s lockout after arrival.

### [P3] Geofence arrival swallowed while a completion is saving
- The new `!isCompleting` guard drops a geofence arrival during an in-flight completion,
  and the geofence won't refire. If the completion then fails, the driver recovers with
  the stop screen's I've Arrived button. Consider surfacing save state and
  `completionError` regardless of status.

### [P2] Live-drivers Firestore listener registration is never removed
- `FirestoreDriverRepository.listenToDrivers` calls `addSnapshotListener` but
  discards the returned `ListenerRegistration`, so the live-drivers listener can
  never be torn down. Callers — `DriverViewModel.startLiveUpdates`,
  `LiveFleetMapView`, `ManageEmployeesView`, `ManagerDriversView`, `ActivityView`
  — leave it running for the whole app session (continued Firestore reads /
  battery after the view is gone, and across sign-out).
- **Not a retain cycle** (handlers already use `[weak self]`); this is resource
  teardown.
- **Fix (scoped, deferred):** return the `ListenerRegistration`, store it, and
  remove it on `.onDisappear`/`deinit` and on sign-out. Touches the
  `DriverRepository` protocol + 5 call sites — deliberately not done in the
  release window to avoid a protocol-wide change; schedule as its own PR.
- **Priority:** Medium.
